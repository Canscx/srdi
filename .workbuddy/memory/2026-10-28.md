## 第二步:打分引擎(已完成,72 条测试通过,commit 59b5af0)

**`pnpm validate` 已扩成三闸**:配置校验 + 三包 typecheck + vitest,提交前必须全绿。

**结构**:`shared/src/scoring/` 19 个文件。规则包出参数,代码只出语义——23 项指标不写 23 份代码,而是 7 个打分器 + 一张 `sourceOf()` 声明表。
关键文件:`normalize.ts`(唯一文本改写层)、`parser.ts`(jsep + AST 硬校验)、`evaluate.ts`(求值器 + 三值逻辑)、`context.ts`(evidence → 值模型)、`indicators/index.ts`(逐指标派生 + 兜底)。

**三种非 JS 语法的最终解法**:
- `fin.revenue[y0]`:jsep 原生可解析,求值时把 computed 的 property 解释为 IndexKey,不注册字面量。
- `[y0..y2]`:必须预处理。`addBinaryOp('..')` **无效**(jsep 先走取成员名分支),改为扫描器(维护引号/圆括号/方括号深度)改写成 `[y0 @ y2]` 并注册 `@`。
- `x#count`:预处理成 `count(x)`。放弃 `addIdentifierChar('#')`,因为它会让 `#foo` 被静默接受。
- `count(x where ...)`:**必须注册 `where` 运算符(优先级 0.5)**。不注册时 jsep 不报错、把 where 当第二实参,语义全错。另加 AST 硬校验:count 只准 1 个参数、where 只能作 count 第一个实参。

**核心语义钉死**:periodic 字段无索引时返回 series,`mean(a/b)` 与 `mean(a)/mean(b)` 是两回事(前者 5.33%,后者 4.29%,测试里锁死)。数组形态(value:[a,b,c])降级 estimated 并打 `period_order_assumed`,因为升序写入会让增长率整体反号且不报错。

**三口径落定**:exclude 项权重从分母移除、其余等比放大到 100(`meta.scale='renormalized'`);guard 失败(净资产≤0)三口径全记 0,不进区间;部分窗口只降 confidence 不改分数;absent 项 official 记 0.5、conservative 0、optimistic 满分。

**实跑发现并修掉的坑**:
1. guard `fin.netAssets > 0` 作用在 series 上,比较直接返回 error,导致 5 个人均/利润率指标(05/06/07/08/11/16)全被误判 notApplicable。修法:比较函数里先把 series 按 ok 槽位取均值降为标量。
2. 解释文案出现"51.92 万元 元/人"双单位。修法:renderExplain 收尾做单位去重。
3. 档位类指标把分数当档位名显示(如"研发机构级别 5")。修法:Derived 增加 label,优先用档位 label。
4. 绿色化称号模板要"项"但给的是折算分。修法:单 term 的 formulaSum 用计数做 displayRaw。

**测试环境坑**:vitest 内部 `cacheFs` 硬编码开启,多 worker 并发写同一临时文件在 Windows 上偶发 `EPERM`,导致部分 spec 文件根本不加载(表现为只跑了 2/5 个文件)。`fileParallelism: false` 解决,5 文件 3 秒。

**实测(虚构 C35 企业,数据齐备)**:official = conservative = optimistic = 79.74,confidence 1.0,六门槛全过;IND_18 排除后权重 5.83 分摊到其余 22 项。
